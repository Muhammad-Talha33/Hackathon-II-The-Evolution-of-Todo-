**Branch**: `005-phase5-partc-cloud-production` | **Date**: 2026-02-08 | **Spec**: [spec.md](./spec.md)

## Summary

Deploy the existing Todo application (Backend, Frontend, Workers with Dapr + Kafka) to a managed Kubernetes cluster with production-grade infrastructure. The implementation creates Kustomize manifests, CI/CD pipelines, observability stack, and production readiness documentation while preserving local docker-compose development unchanged.

**Key Technical Decisions**:
- Kubernetes: DigitalOcean Kubernetes (DOKS)
- Kafka: Confluent Cloud (SASL/SSL)
- Registry: GitHub Container Registry (GHCR)
- Manifests: Kustomize (base + overlays)
- CI/CD: GitHub Actions
- Observability: Prometheus + Grafana + Zipkin

---

## Technical Context

**Language/Version**: YAML (Kubernetes manifests), Bash (scripts), HCL-like (GitHub Actions)
**Primary Dependencies**: Kubernetes 1.28+, Dapr 1.13+, Kustomize 5+, Helm 3.12+
**Storage**: Existing Neon PostgreSQL (external, no changes)
**Testing**: kubectl dry-run, helm lint, kustomize build, GitHub Actions test stage
**Target Platform**: Managed Kubernetes (DigitalOcean DOKS)
**Project Type**: Infrastructure/DevOps (no application code changes)
**Performance Goals**: Pod startup <60s, rolling deployment with zero downtime
**Constraints**: Local docker-compose must remain unchanged, no business logic changes
**Scale/Scope**: 2-node cluster minimum, 3 backend replicas in production

## Implementation Phases

### Phase C-1: Kubernetes Base Manifests (Priority: P0)

**Objective**: Create reusable base manifests for all services with Dapr sidecar injection.

**Tasks**:

1. **Create base namespace manifest**
   - File: `k8s/base/namespace.yaml`
   - Define todo-app namespace with labels
   - Add annotations for ownership

2. **Create backend deployment manifest**
   - File: `k8s/base/backend/deployment.yaml`
   - Add Dapr sidecar injection annotations
   - Configure resource requests/limits
   - Add liveness and readiness probes
   - Reference configmap and secrets

3. **Create backend service manifest**
   - File: `k8s/base/backend/service.yaml`
   - ClusterIP type for internal access
   - Port 8000 targeting backend pods

4. **Create backend configmap**
   - File: `k8s/base/backend/configmap.yaml`
   - Non-sensitive configuration (ENVIRONMENT, LOG_LEVEL)

5. **Create frontend deployment manifest**
   - File: `k8s/base/frontend/deployment.yaml`
   - No Dapr sidecar (frontend doesn't need it)
   - Configure resources and probes
   - Reference configmap for API URL

6. **Create frontend service manifest**
   - File: `k8s/base/frontend/service.yaml`
   - ClusterIP for internal access (Ingress routes externally)

7. **Create reminder worker deployment**
   - File: `k8s/base/workers/reminder-worker-deployment.yaml`
   - Dapr sidecar injection for pub/sub subscription
   - Minimal resource allocation

8. **Create recurrence worker deployment**
   - File: `k8s/base/workers/recurrence-worker-deployment.yaml`
   - Dapr sidecar injection
   - Database connection via secret

9. **Create Dapr pubsub component (cloud Kafka)**
   - File: `k8s/base/dapr/pubsub.yaml`
   - Type: pubsub.kafka
   - Reference Kubernetes secrets for credentials
   - SASL/SSL configuration

10. **Create Dapr statestore component**
    - File: `k8s/base/dapr/statestore.yaml`
    - Type: state.redis
    - Optional for Phase C (can use in-cluster Redis)

11. **Create Dapr cron binding**
    - File: `k8s/base/dapr/cron-binding.yaml`
    - Schedule: @every 1m
    - Route: /cron/check-reminders

12. **Create Dapr configuration (observability)**
    - File: `k8s/base/dapr/configuration.yaml`
    - Enable tracing to Zipkin
    - Enable metrics for Prometheus

13. **Create base kustomization.yaml**
    - File: `k8s/base/kustomization.yaml`
    - List all resources
    - Define common labels

**Validation**:
```bash
kustomize build k8s/base | kubectl apply --dry-run=client -f -
```

**Exit Criteria**:
- All manifests pass dry-run validation
- Dapr annotations are present on backend and worker deployments
- Resource limits are defined for all containers

### Phase C-2: Environment Overlays (Priority: P0)

**Objective**: Create staging and production overlays with environment-specific configuration.

**Tasks**:

1. **Create staging namespace**
   - File: `k8s/overlays/staging/namespace.yaml`
   - Namespace: todo-staging
   - Environment label: staging

2. **Create staging kustomization**
   - File: `k8s/overlays/staging/kustomization.yaml`
   - Reference base resources
   - Set namespace to todo-staging
   - Apply staging patches

3. **Create staging replica count patch**
   - File: `k8s/overlays/staging/patches/replica-count.yaml`
   - Backend: 1 replica
   - Frontend: 1 replica
   - Workers: 1 replica each

4. **Create staging resource limits patch**
   - File: `k8s/overlays/staging/patches/resource-limits.yaml`
   - Conservative limits for staging

5. **Create staging secrets template**
   - File: `k8s/overlays/staging/secrets.yaml.template`
   - Template with placeholders (never actual values)
   - Documentation for required secrets

6. **Create production namespace**
   - File: `k8s/overlays/production/namespace.yaml`
   - Namespace: todo-production
   - Environment label: production

7. **Create production kustomization**
   - File: `k8s/overlays/production/kustomization.yaml`
   - Reference base resources
   - Set namespace to todo-production
   - Apply production patches

8. **Create production replica count patch**
   - File: `k8s/overlays/production/patches/replica-count.yaml`
   - Backend: 3 replicas
   - Frontend: 2 replicas
   - Workers: 2 replicas each

9. **Create production resource limits patch**
   - File: `k8s/overlays/production/patches/resource-limits.yaml`
   - Elevated limits for production traffic

10. **Create production ingress**
    - File: `k8s/overlays/production/ingress.yaml`
    - NGINX ingress class
    - Path routing: /api → backend, / → frontend
    - TLS configuration (optional for Phase C)

11. **Create production secrets template**
    - File: `k8s/overlays/production/secrets.yaml.template`
    - Same structure as staging

**Validation**:
```bash
kustomize build k8s/overlays/staging | kubectl apply --dry-run=client -f -
kustomize build k8s/overlays/production | kubectl apply --dry-run=client -f -
```

**Exit Criteria**:
- Staging and production overlays build without errors
- Namespace is correctly set in generated manifests
- Replica counts differ between environments
- Ingress only appears in production overlay

### Phase C-3: CI/CD Pipeline (Priority: P1)

**Objective**: Automate testing, building, and deployment via GitHub Actions.

**Tasks**:

1. **Create CI workflow**
   - File: `.github/workflows/ci.yaml`
   - Trigger: push to main, pull requests
   - Jobs: lint, test, build, push
   - Build multi-platform images (amd64)
   - Push to GHCR with SHA tag

2. **Create CD staging workflow**
   - File: `.github/workflows/cd-staging.yaml`
   - Trigger: successful CI on main
   - Deploy to staging namespace
   - Wait for rollout
   - Run smoke tests

3. **Create CD production workflow**
   - File: `.github/workflows/cd-production.yaml`
   - Trigger: manual workflow_dispatch
   - Require environment approval
   - Deploy to production namespace
   - Verify health after deployment

4. **Configure repository secrets**
   - Document required secrets:
     - KUBE_CONFIG (base64 encoded kubeconfig)
     - GHCR_TOKEN (GitHub token for registry)
   - Add to repository settings

5. **Create deployment script**
   - File: `scripts/deploy-k8s.sh`
   - Apply secrets (from secure source)
   - Apply Kustomize overlay
   - Wait for rollout
   - Verify health

**Validation**:
- Push to branch, verify CI runs
- Merge to main, verify staging deployment
- Trigger production manually, verify approval required

**Exit Criteria**:
- CI workflow builds and pushes images
- Staging deploys automatically on main push
- Production requires manual approval
- Rollback is documented and tested

### Phase C-4: Observability Stack (Priority: P2)

**Objective**: Deploy monitoring, logging, and tracing infrastructure.

**Tasks**:

1. **Create observability namespace**
   - Separate namespace for monitoring tools
   - Resource quotas (optional)

2. **Create Prometheus values file**
   - File: `k8s/observability/prometheus-values.yaml`
   - Scrape config for backend, frontend, workers
   - Dapr sidecar metrics scraping
   - Retention period: 15 days

3. **Create Grafana values file**
   - File: `k8s/observability/grafana-values.yaml`
   - Prometheus datasource
   - Admin credentials from secret
   - Dashboard provisioning

4. **Create Todo App Grafana dashboard**
   - File: `k8s/observability/grafana-dashboards/todo-app.json`
   - Request rate panel
   - Latency percentiles panel
   - Error rate panel
   - Pod health panel

5. **Create Zipkin deployment**
   - File: `k8s/observability/zipkin.yaml`
   - Simple deployment for distributed tracing
   - Service for internal access

6. **Update Dapr configuration**
   - Point tracing to Zipkin service
   - Enable metric collection

**Validation**:
```bash
helm install prometheus prometheus-community/prometheus \
  -n observability -f k8s/observability/prometheus-values.yaml --dry-run
kubectl apply -f k8s/observability/zipkin.yaml --dry-run=client
```

**Exit Criteria**:
- Prometheus scrapes all services
- Grafana dashboard shows metrics
- Zipkin displays distributed traces
- Dapr tracing is configured

## Risk Mitigation

| Risk | Mitigation |
|------|------------|
| Cloud Kafka connection fails | Test with local Redpanda first, then migrate to cloud with SASL credentials |
| Image pull errors | Pre-configure GHCR pull secret in namespaces |
| Dapr sidecar injection fails | Verify Dapr installation with `dapr status -k` before deploying apps |
| Rollout hangs | Configure appropriate probe timeouts and failure thresholds |
| Secrets exposure | Use templates (`.template` suffix), never commit actual secrets |
